# ТЗ: Миграция секретов проекта на GitHub Secrets

## Контекст и причина изменения

Текущая версия бота хранит все секреты (Upwork Client ID/Secret, Telegram Bot Token/Chat ID) открытым текстом прямо в `src/config.js`, закоммиченном в репозиторий. Это было осознанным решением на старте разработки, обоснованным тем, что репозиторий приватный — риск утечки секретов при таком раскладе минимален.

В процессе эксплуатации бот уткнулся в лимит бесплатного тарифа GitHub Actions для приватных репозиториев (2000 минут/месяц). При интервале запуска раз в 5 минут это исчерпывается быстрее, чем ожидалось. Ниже — скриншот реальной ошибки, полученной в проекте:

![GitHub Actions billing error](./assets/github_actions_billing_error.png)

Текст ошибки: *"The job was not started because recent account payments have failed or your spending limit needs to be increased. Please check the 'Billing & plans' section in your settings."*

**Важно:** это не сбой оплаты и не реальное списание денег. По умолчанию у бесплатного аккаунта GitHub установлен лимит расходов $0 — это защитный механизм: при исчерпании бесплатных минут задачи просто перестают запускаться, а не начинают тратить деньги владельца аккаунта. То есть ошибка означает "бесплатный лимit минут закончился", а не "с карты списали лишнее" или "с картой что-то не так".

**Один из рассматриваемых вариантов решения** — сделать репозиторий публичным, поскольку для публичных репозиториев GitHub Actions на стандартных раннерах полностью бесплатен и не ограничен по минутам. Однако публичный репозиторий делает небезопасным нынешний подход хранения секретов прямо в коде — любой сможет открыть `config.js` и увидеть боевые ключи от Upwork API и Telegram-бота.

**Вывод:** прежде чем рассматривать переход на публичный репозиторий (или просто из общих соображений безопасности, даже если репозиторий останется приватным), нужно вынести секреты из кода в GitHub Secrets — встроенный защищённый механизм хранения конфиденциальных значений, которые не отображаются в коде репозитория и доступны только во время выполнения workflow.

## Задача для разработчика

### Шаг 1. Добавить секреты в настройках репозитория

1. Repository → **Settings** → **Secrets and variables** → **Actions**.
2. Кнопка **"New repository secret"** — создать четыре секрета:
   - `UPWORK_CLIENT_ID`
   - `UPWORK_CLIENT_SECRET`
   - `TELEGRAM_BOT_TOKEN`
   - `TELEGRAM_CHAT_ID`

Значения взять из текущего `src/config.js` (до его правки на шаге 2).

### Шаг 2. Переделать `src/config.js` — читать секреты из переменных окружения

**Было:**
```js
module.exports = {
  UPWORK_CLIENT_ID: "конкретное_значение",
  UPWORK_CLIENT_SECRET: "конкретное_значение",
  TELEGRAM_BOT_TOKEN: "конкретное_значение",
  TELEGRAM_CHAT_ID: "конкретное_значение",
  // ... остальной конфиг без изменений
};
```

**Стало:**
```js
module.exports = {
  UPWORK_CLIENT_ID: process.env.UPWORK_CLIENT_ID,
  UPWORK_CLIENT_SECRET: process.env.UPWORK_CLIENT_SECRET,
  TELEGRAM_BOT_TOKEN: process.env.TELEGRAM_BOT_TOKEN,
  TELEGRAM_CHAT_ID: process.env.TELEGRAM_CHAT_ID,
  // ... остальной конфиг (KEYWORDS, FILTERS, SCORING_WEIGHTS, PATHS) без изменений —
  // это не секретные данные, их не трогаем
};
```

### Шаг 3. Прокинуть секреты в workflow

В `.github/workflows/poll.yml`, в шаге запуска скрипта, добавить блок `env`:

```yaml
- name: Run job poller
  run: node src/index.js
  env:
    UPWORK_CLIENT_ID: ${{ secrets.UPWORK_CLIENT_ID }}
    UPWORK_CLIENT_SECRET: ${{ secrets.UPWORK_CLIENT_SECRET }}
    TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
    TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}
```

### Шаг 4. Отдельный вопрос — `data/token.json`

Этот файл — не статичный секрет, а состояние, которое **обновляется при каждом запуске** (см. `src/auth.js`: `refresh_token` обменивается на новый `access_token`, файл перезаписывается). GitHub Secrets для этого не подходит напрямую — секреты не предназначены для автоматической перезаписи workflow'ом на лету без специальных дополнительных прав.

**Развилка, которую нужно закрыть перед реализацией:**

- **Если репозиторий остаётся приватным** — `data/token.json` можно оставить как есть, обычным закоммиченным файлом. Секретами делаем только Шаги 1-3 (Client ID/Secret, Telegram-токены). Угрозы нет, т.к. доступ к репозиторию ограничен.

- **Если репозиторий станет публичным** — `token.json` тоже нельзя коммитить открыто. Нужно:
  1. Завести ещё один секрет `UPWORK_REFRESH_TOKEN` с текущим значением `refresh_token`.
  2. Переписать `src/auth.js`: вместо чтения/записи файла — получать `access_token` из `process.env.UPWORK_REFRESH_TOKEN` при каждом запуске, не сохраняя результат никуда постоянно (действует в рамках одного запуска и исчезает).
  3. **Важно проверить на практике:** меняет ли Upwork сам `refresh_token` при каждом обмене на `access_token`, или `refresh_token` статичен и переиспользуется многократно. Если Upwork ротирует `refresh_token` при каждом использовании (частая практика в OAuth 2.0) — тогда потребуется механизм обновления самого секрета `UPWORK_REFRESH_TOKEN` через GitHub API (`gh secret set` из workflow с токеном, имеющим права на запись секретов), что существенно усложняет реализацию.

**Решение по этому пункту нужно принять до начала кодинга** — от него зависит объём работы на Шаге 4.

## Контрольный список после реализации

- [ ] Секреты созданы в Settings → Secrets and variables → Actions
- [ ] `config.js` не содержит ни одного захардкоженного значения токена/ключа
- [ ] `poll.yml` пробрасывает секреты через `env`
- [ ] Проверено, что `git log` / история коммитов не содержит старых версий `config.js` с открытыми секретами (если содержит — старые ключи считаются скомпрометированными и подлежат ротации на стороне Upwork/Telegram, т.к. история публичного репозитория видна всем, а даже в приватном — всем, кто получит доступ к репо)
- [ ] Принято решение по `data/token.json` (приватный репо — не трогаем / публичный репо — переделываем по варианту Б)
- [ ] Ручной тестовый запуск workflow (`workflow_dispatch`) подтверждает, что скрипт корректно получает значения из `process.env` и работает как раньше
